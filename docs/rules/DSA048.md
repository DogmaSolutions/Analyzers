# DSA048

Do not wait for a change of state by sleeping in a loop.

| Property     | Value                                                                                          |
|:-------------|:-----------------------------------------------------------------------------------------------|
| Rule ID      | DSA048                                                                                        |
| Title        | Do not wait for a change of state by sleeping in a loop                                       |
| Category     | Code Smell                                                                                    |
| Severity     | ⚠ Warning                                                                                     |
| Refactoring available | ❌                                                                                             |
| Code-review tools available | ✅                                                                                             |
| Is enabled   | ✅                                                                                             |

## 💡 Rationale

When a thread has to wait for something another thread does, the quickest thing to write is a loop: *"is it done? no. sleep a bit. is it done? no. sleep a bit..."*

```csharp
public void WaitUntilConnected()
{
    while (!_connected)            // DSA048
    {
        Thread.Sleep(50);
    }
}
```

It works on the developer's machine, and it hides four problems:

| Problem | What happens |
|:--------|:-------------|
| **It can wait forever** | If the thread that should set `_connected` fails, stops, or is never started, this one never returns. The caller hangs, with no error and no log |
| **Latency** | The change is noticed up to one sleep interval late, on **every** change. Shorter sleeps mean more wake-ups, longer ones mean slower reactions |
| **Wasted work** | The thread wakes up over and over to learn nothing, and keeps a pool thread (or a core) busy for the whole wait |
| **A hidden contract** | Nothing says who is supposed to change the field, when, and what happens if it never does. The visibility of the field is a question as well: see [DSA010](DSA010.md) and [DSA046](DSA046.md) |

The same applies to `await Task.Delay(...)` in the loop (the thread is released, but the polling remains), and to `Task.Delay(...).Wait()`.

## ✅ What is reported

A `while` or `do ... while` loop whose body calls `Thread.Sleep` or `Task.Delay` (not inside a lambda or a local function), and whose **condition reads the state of its own class**: a field, a property or a method of the class or of its base classes, directly or through `this`, or the first element of a chain (`_connection.IsOpen`).

| Scenario | Message |
|:---------|:--------|
| Nothing in the loop looks at the clock or at a cancellation request | **No way to give up**: waits forever if the other side never signals |
| The loop looks at the clock (`DateTime.Now`/`UtcNow`, `Stopwatch`, `Environment.TickCount`...), at a `CancellationToken`, or at something called *timeout* or *deadline* | **With a timeout**: good, but still polling |

The diagnostic is located on the `while (...)` header, and the message names the state the loop waits for and the wait it uses.

## 🚫 What is *not* reported

| Case | Why |
|:-----|:----|
| The condition only reads locals, parameters, constants, `readonly` fields on their own, or members of other types (`File.Exists(path)`, `process.HasExited`) | The loop is not waiting for the state of the class: polling an external resource (a file, a process, a device) often has no event to wait for |
| `while (true) { ... Thread.Sleep(...); }` | A periodic worker, not a wait for a change. Use `PeriodicTimer` or a `Timer`, but this is another lesson |
| The loop changes the state it checks (`_attempt++`, `_ready = Check();`, `Interlocked.Increment(ref _count)`) | The loop makes progress by itself: a retry loop, not a wait for another thread |
| `Thread.Sleep` in a lambda or a local function declared inside the loop | It does not pause the loop |
| `Thread.Yield`, `SpinWait` | Not sleeping |
| Generated files | `*.Designer.cs`, `*.g.cs`... are ignored |

## 🔧 Alternatives

| You want | Use |
|:---------|:----|
| A thread to wait for an event once | `ManualResetEventSlim.Wait(timeout, token)`, set by the other thread |
| A thread to wait for a count of events | `SemaphoreSlim.Wait(timeout, token)` / `WaitAsync`, or `CountdownEvent` |
| An async method to wait for a result | `TaskCompletionSource<T>` (created with `TaskCreationOptions.RunContinuationsAsynchronously`) |
| Producers and consumers | `Channel<T>` / `BlockingCollection<T>` |
| Wait for a condition under a lock | `Monitor.Wait` / `Monitor.PulseAll` on the same private lock object ([DSA047](DSA047.md)) |
| A periodic job | `PeriodicTimer` / `System.Threading.Timer` |

```csharp
private readonly ManualResetEventSlim _connected = new ManualResetEventSlim();

public bool WaitUntilConnected(TimeSpan timeout, CancellationToken token)
{
    return _connected.Wait(timeout, token);       // returns false after the timeout: the caller decides
}

private void OnConnected()
{
    _connected.Set();                             // wakes the waiters at once
}
```

Whatever the mechanism, **always wait with a timeout and a `CancellationToken`**, and decide what the caller does when the wait fails.

## 🔧 Code fix

* **Add comment for code review**: inserts a comment that references the rule. Replacing a polling loop with a signal changes who signals, who waits and for how long, which is a design decision, so no automatic rewrite is offered.

## ⚙ Options

All options are set in the `.editorconfig`, under `dotnet_diagnostic.DSA048.<key>`.

| Key | Default | Meaning |
|:----|:--------|:--------|
| `severity` | `warning` | The severity of the rule |
| `report_loops_with_timeout` | `true` | Report the loops that give up after a timeout or a cancellation (they still poll) |
| `include_task_delay` | `true` | Report the loops that wait with `Task.Delay` too |
| `include_do_loops` | `true` | Report `do ... while` loops too |
| `excluded_type_name_patterns` | *(empty)* | Glob patterns of the type names to ignore |
| `excluded_namespace_patterns` | *(empty)* | Glob patterns of the namespaces to ignore |
| `excluded_base_types` | *(empty)* | Types whose descendants are ignored |
| `excluded_member_name_patterns` | *(empty)* | Glob patterns of the member names to ignore |
| `excluded_file_patterns` | `*.Designer.cs, *.generated.cs, *.g.cs, *.g.i.cs` | Glob patterns of the files to ignore |

```ini
[*.cs]
dotnet_diagnostic.DSA048.severity = warning
dotnet_diagnostic.DSA048.report_loops_with_timeout = false
dotnet_diagnostic.DSA048.excluded_member_name_patterns = Wait*
```

## 🔐 Security implications

A wait that never ends is a denial of service waiting to happen: a request thread stuck in a polling loop is never given back to the pool.

* **CWE-833** — [Deadlock](https://cwe.mitre.org/data/definitions/833.html)
* **CWE-835** — [Loop with Unreachable Exit Condition ("Infinite Loop")](https://cwe.mitre.org/data/definitions/835.html)
* **CWE-400** — [Uncontrolled Resource Consumption](https://cwe.mitre.org/data/definitions/400.html)
