# DSA040

Do not use `System.Random` for security-sensitive values.

| Property     | Value                                                                                          |
|:-------------|:-----------------------------------------------------------------------------------------------|
| Rule ID      | DSA040                                                                                        |
| Title        | Do not use System.Random for security-sensitive values                                        |
| Category     | Security                                                                                      |
| Severity     | ⚠ Warning                                                                                     |
| Refactoring available | ❌                                                                                             |
| Code-review tools available | ❌                                                                                             |
| Is enabled   | ✅                                                                                             |

## Rationale

`System.Random` is a fast **non-cryptographic** pseudo-random generator; its output is predictable. Using it for a security-sensitive value — a token, password, salt, nonce, IV, session id, API key, OTP or CSRF token — lets an attacker who can observe or reconstruct the generator state predict or forge those secrets.

```csharp
// BUG: a guessable password-reset token.
var resetToken = rnd.Next().ToString();
```

This rule flags `System.Random` output (any `Next*` method — including `Random.Shared` — and `NextBytes` into a buffer) that flows into a **security-named sink**. The sink name is matched on **word boundaries**, so `apiKey` and `sessionId` match while `keyboard` does not. It follows one assignment hop within a method.

### Fix

Use `System.Security.Cryptography.RandomNumberGenerator`:

```csharp
// 256-bit token:
string resetToken = Convert.ToHexString(RandomNumberGenerator.GetBytes(32));

// bounded value without modulo bias (see DSA039):
int otp = RandomNumberGenerator.GetInt32(0, 1_000_000);
```

### Relationship to CA5394

The built-in `CA5394` ("Do not use insecure randomness") flags **every** `System.Random` use, which is noisy. DSA040 is deliberately **sink-aware**: it fires only when the value is used for something whose name says it is a secret, giving a low false-positive signal. Keep DSA040 at `warning`; if `CA5394` is too noisy for your codebase you can dial it down without losing the high-signal security cases DSA040 covers.

### Security mapping

- **CWE-338: Use of Cryptographically Weak Pseudo-Random Number Generator (PRNG).**

## Matched patterns (code is NOT OK)

```cs
var token = rnd.Next().ToString();          // security-named local
sessionId = rnd.Next();                       // assignment to a security-named field
public int GetOtp() => rnd.Next();            // security-named method return
rnd.NextBytes(salt);                          // NextBytes into a security-named buffer
var t = rnd.Next(); apiKey = t;               // one assignment hop
```

## Not matched patterns (code is OK)

```cs
int diceRoll = rnd.Next(1, 7);                // non-security sink
var keyboardShortcut = rnd.Next();            // 'key' only as a substring — not a word boundary
var apiKey = RandomNumberGenerator.GetBytes(32); // already using the strong API
```

## Scope / non-goals

- Lightweight **name heuristic**, not an interprocedural taint engine.
- Follows a single local assignment hop; deeper or cross-method flow is out of scope (precision over recall).
- The security term set: token, password, passwd, pwd, salt, nonce, iv, secret, apikey, session, sessionid, csrf, otp, key, resetcode, verificationcode.

## Rule configuration

In order to change the severity level of this rule, change/add this line in the `.editorconfig` file:

```ini
# DSA040: Do not use System.Random for security-sensitive values
dotnet_diagnostic.DSA040.severity = warning
```
