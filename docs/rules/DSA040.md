# DSA040

`System.Random` is a non-cryptographic pseudo-random generator: its output is fast but predictable, and must never be used to produce security-sensitive values such as tokens, passwords, salts, nonces, initialization vectors, session identifiers, API keys, OTPs or CSRF tokens. This rule flags `Random` output that flows into a sink whose name matches a security term, complementing the broad CA5394 with a low-noise, sink-aware signal.

## 💡 Rationale

`System.Random` is a fast **non-cryptographic** pseudo-random generator; its output is predictable. Using it for a security-sensitive value — a token, password, salt, nonce, IV, session id, API key, OTP or CSRF token — lets an attacker who can observe or reconstruct the generator state predict or forge those secrets.

```csharp
// BUG: a guessable password-reset token.
var resetToken = rnd.Next().ToString();
```

This rule flags `System.Random` output (any `Next*` method — including `Random.Shared` — and `NextBytes` into a buffer) that flows into a **security-named sink**: a variable, field, property, parameter or return whose identifier contains a security word on a word boundary (so `apiKey` and `sessionId` match while `keyboard` does not). It follows one assignment hop within a method and favours precision over recall — it is a lightweight name heuristic, not a taint engine. The recognised terms are: `token`, `password`, `passwd`, `pwd`, `salt`, `nonce`, `iv`, `secret`, `apikey`, `session`, `sessionid`, `csrf`, `otp`, `key`, `resetcode`, `verificationcode`.

## 🔐 Security implications

- **CWE-338: Use of Cryptographically Weak Pseudo-Random Number Generator (PRNG)** — `System.Random` is not suitable for secrets; an attacker who reconstructs its state can forge or guess the produced tokens, salts, nonces, keys and OTPs.
- **OWASP: Insecure Randomness** — the canonical class of defect where predictable randomness is used where unpredictability is a security requirement.

## 🔦 Code sample

```csharp
public class PasswordReset
{
    private readonly Random _rnd = new Random();

    public string CreateToken_NotOk()
    {
        // this WILL trigger the rule: Random output flows into a security-named sink
        var resetToken = _rnd.Next().ToString();
        return resetToken;
    }

    public string CreateToken_Ok()
    {
        // this WILL NOT trigger the rule: cryptographic generator
        return Convert.ToHexString(RandomNumberGenerator.GetBytes(32));
    }
}
```

## ℹ️  Matched patterns (code is NOT OK)

```cs
var token = rnd.Next().ToString();          // security-named local
sessionId = rnd.Next();                       // assignment to a security-named field
public int GetOtp() => rnd.Next();            // security-named method return
rnd.NextBytes(salt);                          // NextBytes into a security-named buffer
var t = rnd.Next(); apiKey = t;               // one assignment hop
```

## ✅ Not matched patterns (code is OK)

```cs
int diceRoll = rnd.Next(1, 7);                // non-security sink
var keyboardShortcut = rnd.Next();            // 'key' only as a substring — not a word boundary
var apiKey = RandomNumberGenerator.GetBytes(32); // already using the strong API
```

## 👉️ Rules of thumb for prevention and proactive posture

- Use `System.Security.Cryptography.RandomNumberGenerator` for every security-sensitive value:

  ```csharp
  // 256-bit token:
  string resetToken = Convert.ToHexString(RandomNumberGenerator.GetBytes(32));

  // bounded value without modulo bias (see DSA039):
  int otp = RandomNumberGenerator.GetInt32(0, 1_000_000);
  ```

- **Relationship to CA5394**: the built-in `CA5394` ("Do not use insecure randomness") flags **every** `System.Random` use, which is noisy. DSA040 is deliberately **sink-aware**: it fires only when the value is used for something whose name says it is a secret, giving a low false-positive signal. Keep DSA040 at `warning`; if `CA5394` is too noisy you can dial it down without losing the high-signal cases DSA040 covers.
- Because DSA040 is a name heuristic that follows a single local hop, treat "use `RandomNumberGenerator` for secrets" as the team default rather than relying on the analyzer to catch every case.

## ⚙️ Rule configuration

```ini
# DSA040: Do not use System.Random for security-sensitive values
dotnet_diagnostic.DSA040.severity = error
```
