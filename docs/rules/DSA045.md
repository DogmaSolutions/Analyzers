# DSA045

The exclusion from the code coverage must match the nature of the type: a pure data carrier (DTO) should be excluded with `[ExcludeFromCodeCoverage]`, and a type with logic should **not** be.

| Property     | Value                                                                                          |
|:-------------|:-----------------------------------------------------------------------------------------------|
| Rule ID      | DSA045                                                                                        |
| Title        | The exclusion from the code coverage must match the nature of the type: a pure data carrier should be excluded, a type with logic should not |
| Category     | Best Practice                                                                                 |
| Severity     | ⚠ Warning                                                                                     |
| Refactoring available | ✅                                                                                             |
| Code-review tools available | ✅                                                                                             |
| Is enabled   | ✅                                                                                             |

## 💡 Rationale

A *pure data carrier* (a DTO, a request or response model, a settings object, an entity with no behavior...) is a type made only of properties: no logic, no explicit constructor, and base types that are data carriers too.

```csharp
public class OrderDto
{
    public int Id { get; set; }
    public string Customer { get; set; }
    public decimal Total { get; set; }
}
```

There is nothing in it that can be wrong, so there is nothing a test can verify. Yet the coverage tools count its lines, and the figure they produce is distorted in one of two ways:

| What happens | Effect on the metric |
|:-------------|:---------------------|
| The tests of other classes create the DTO and set a few properties "in passing" | The DTO shows as *covered*: the percentage **goes up** without a single assertion about it. This is **green washing**: the number says "verified" about code that was never at risk |
| Nothing creates it (a response model, an unused property) | The DTO shows as *uncovered*: the percentage **goes down**, and the team is pushed to write meaningless tests just to move the number |

In both cases the coverage stops answering the question it exists for: *how much of the code that can break is verified?* Excluding the DTOs from the measure keeps the figure about the logic.

The rule reports a pure data carrier that is **not** excluded yet, and the code fix adds the attribute.

> The rule is *only* about types without logic. It stays silent as soon as the type, or one of its base types, contains a method, a constructor, a computed property... A type must not be excluded from the coverage to hide logic that nobody tests: if you ever add behavior to an excluded DTO, remove the attribute (the rule will not tell you, so review the exclusion when you review the type).

### The opposite scenario: a type with logic that is excluded

The attribute is a statement: *"there is nothing to test in this type"*. It is true for a DTO and false for a type that has logic:

```csharp
[ExcludeFromCodeCoverage]            // DSA045: the type has logic
public class PriceCalculator
{
    public decimal Total(decimal net, decimal vat) => net + net * vat;
}
```

The calculation is code that can break, and the attribute hides it from the coverage figure: nobody is pushed to test it, and the percentage looks better than the truth. It is the same distortion as in the first scenario, in the opposite direction, and a more dangerous one: a DTO that is not excluded makes the figure *lower*, a logic that is excluded makes it *look healthy*.

The rule reports a type that is decorated with the attribute **on the type itself** (or on any part of a `partial` type) and is **not** a pure data carrier (same definition as below). The message names the first piece of logic that it found (*"it contains the method 'Total'"*, *"an explicit constructor"*, *"the property 'X', which does more than store a value"*...), and the code fix *Remove [ExcludeFromCodeCoverage]* removes the attribute from every part of the type, keeping the other attributes, the documentation and the indentation.

What is deliberately **not** looked at, to stay precise:

* only the members of the type itself are inspected: a DTO whose *base type* has logic is not reported (the attribute excludes the lines of the DTO only);
* a type that is excluded because a *containing type*, or the whole *assembly*, has the attribute (the type has no attribute of its own to remove);
* types excluded by the options, generated code and test projects, as in the first scenario.

If the logic really cannot be tested (a composition root, a UI event handler...), exclude *those members* (`[ExcludeFromCodeCoverage]` can be applied to methods, properties, constructors and events) and keep the rest of the type measured; or, as a last resort, silence the rule for the type with `excluded_type_name_patterns` or `report_excluded_types_with_logic = false`.

### What is a "pure" data carrier?

| Member | Pure? |
|:-------|:------|
| Auto-property (`{ get; set; }`, `{ get; init; }`, `{ get; }`, private setters, `required`, `virtual`, `abstract`) | ✅ |
| Old-style property over a private field that an auto-property could replace: `get { return _a; } set { _a = value; }` (also with expression bodies, `this._a`, `init`, a private setter, or get-only) | ✅ (`allow_backing_field_properties`); the field is not counted as a data member of its own |
| Property initializer made of a literal, a constant, `default`, `typeof`, `string.Empty`, `new()`, `new List<T>()`, `[]`, an array or an object initializer of such values | ✅ (`allow_property_initializers`) |
| Property initializer that *calls* something (`Guid.NewGuid()`, `Array.Empty<T>()`, a conditional...) | ❌ |
| Instance field (a public field of an old-style DTO) | ✅ (`allow_fields`) |
| Constant | ✅ (ignored) |
| Positional record parameters (`record Dto(int A, string B);`) | ✅ |
| Expression-bodied property, property with an accessor body | ❌ (✅ with `allow_computed_properties`) |
| Explicit constructor | ❌ (an empty parameterless one is ✅ with `allow_parameterless_constructor`) |
| Primary constructor of a **class** or **struct** | ❌ (it is logic: it takes parameters and initializes) |
| Method, operator, conversion operator, indexer, event, finalizer, static constructor | ❌ |
| Static property or field | ❌ |
| Nested type | ❌ (✅ with `allow_nested_types`) |

The members the compiler generates for a `record` (equality, `ToString`, `Clone`, `Deconstruct`) are not logic written by anyone, and are ignored.

### Old-style properties

A property written the old way is an auto-property in disguise, and has no more logic than one:

```csharp
private int _quantity;
public int Quantity
{
    get { return _quantity; }
    set { _quantity = value; }
}
```

It is data, with the following conditions (all of them, otherwise it is logic and the type is not a data carrier):

* the getter only returns a field, and the setter (if any) only assigns `value` to *the same* field (`return _a;`, `_a = value;`, `=> _a`, `=> _a = value`, `this._a`, parentheses);
* the field is **private**, of an instance, **not `volatile`**, and of **exactly the type of the property** (no conversion);
* the field is backing **only that property**: if two properties share it, no auto-property could replace them;
* a `readonly` field is accepted only when there is no setter;
* its initializer, if any, is a simple one (same rules as the other initializers).

The backing field is not a data member of its own: it does not count in the number of members and it is not affected by `allow_fields`. A method that uses the field makes the type a type with logic anyway. For the base types read from metadata, where the bodies cannot be seen, the private fields are ignored for the same reason.

Set `allow_backing_field_properties = false` to consider these properties as logic, e.g. when you want the old style to be modernized before excluding the type.

### The base types

A type that derives from a class with logic is not a pure data carrier, so the **whole inheritance chain** is inspected (`inspect_base_types`, on by default):

| Base type | How it is inspected |
|:----------|:--------------------|
| In the same solution (source) | With exactly the same rules as the type itself |
| In a referenced assembly (metadata) | By its *shape*, because its bodies are not visible: properties and fields, and a parameterless constructor, make it a data carrier; any method, operator, event, indexer, static member or constructor with parameters makes it **impure**. This is a *best effort*: a computed property of a compiled base type cannot be seen |
| `object`, `ValueType` | Ignored |
| Cannot be resolved (missing reference) | Never assumed to be a data carrier: nothing is reported |
| Listed in `excluded_base_types` | Nothing is reported for the types that derive from it |

Framework types such as `Exception`, `List<T>` or `Attribute` have methods, so what derives from them is not a data carrier.

### What is never reported

* a pure data carrier that already has `[ExcludeFromCodeCoverage]` (also on another part of a `partial` type, or on a containing type, or on the assembly: `[assembly: ExcludeFromCodeCoverage]`);
* a type marked as generated (`[GeneratedCode]`, `[CompilerGenerated]`), and generated files;
* the types of a **test project** (an assembly that references a test framework: xUnit, NUnit, MSTest, TUnit), where the coverage is not measured;
* static classes, interfaces, enums and delegates;
* types excluded by the options.

## 🔦 Code sample

```csharp
// this WILL trigger the rule: nothing but properties
public class OrderDto
{
    public int Id { get; set; }
    public string Customer { get; set; } = string.Empty;
    public List<string> Lines { get; set; } = new();
}

// this WILL NOT trigger the rule: already excluded
[ExcludeFromCodeCoverage]
public class CustomerDto
{
    public int Id { get; set; }
}

// this WILL NOT trigger the rule: it has logic
public class Invoice
{
    public decimal Net { get; set; }
    public decimal Vat { get; set; }
    public decimal Total() => Net + Vat;
}

// this WILL NOT trigger the rule: the base type has logic
public class SpecialOrderDto : OrderBase
{
    public string Note { get; set; } = string.Empty;
}
```

## ℹ️  Matched patterns (code is NOT OK)

```cs
public class A { public int X { get; set; } }                                 // properties
public class B { public int X { get; init; } public string Y { get; } }       // init and get-only properties
public class C : A { public int Z { get; set; } }                             // a data carrier derived from a data carrier
public class D { public List<int> Items { get; set; } = new(); }              // simple initializers
public class E { public int X; public string Y; }                             // fields (allow_fields)
public class E2 { private int _x; public int X { get { return _x; } set { _x = value; } } } // old-style property (allow_backing_field_properties)
public abstract class F { public abstract int X { get; set; } }               // abstract classes (include_abstract_classes)

// records and structs are looked at as well (included_type_kinds):
public record G(int X, string Y);                                             // positional record
public record struct H(int X);
public struct I { public int X { get; set; } }
```

## ✅ Not matched patterns (code is OK)

```cs
[ExcludeFromCodeCoverage] public class A { public int X { get; set; } }      // already excluded
public class B { public int X { get; set; } public int Twice() => X * 2; }   // a method
public class C { public int X { get; set; } public int Twice => X * 2; }     // a computed property
public class C2 { private int _x; public int X { get { return _x; } set { if (value > 0) _x = value; } } } // a setter with logic
public class D { public D(int x) { X = x; } public int X { get; } }          // a constructor
public class E { public Guid Id { get; set; } = Guid.NewGuid(); }            // an initializer that runs code
public class F : Exception { public int X { get; set; } }                    // a base type with logic
public class G { public static int Count { get; set; } public int X { get; set; } } // a static member
public class H { }                                                           // no data at all (min_data_members)
public class OrderDto { public int X { get; set; } }                         // with excluded_type_name_patterns = *Dto
```

## 👉️ Rules of thumb for prevention and proactive posture

- Keep the data carriers free of logic. As soon as a DTO needs validation, mapping or formatting, it has become a class with behavior, and **that** behavior deserves tests (and coverage).
- Put the mapping logic in a mapper or a service, and test *that*.
- Prefer excluding with the attribute (it travels with the type) over a long list of patterns in the coverage tool configuration.
- Exclude *types*, not whole projects or folders: a folder of "models" tends to collect, over time, types that gain logic.
- If you use a coverage tool that ignores the attribute, configure it to honor it (Coverlet and Visual Studio do), or use `exclusion_attributes` to name the attribute your tool understands.

## 🛠️ Included Code Fixer and Mitigation

For a type with logic that is excluded, the code fix *Remove [ExcludeFromCodeCoverage]* removes the attribute (see above). For a pure data carrier, the code fix *Add [ExcludeFromCodeCoverage]* adds the attribute to the type, as a new line above the existing attributes and below the documentation, and adds `using System.Diagnostics.CodeAnalysis;` when it is missing (a file header such as a license stays on top). On a `partial` type the attribute goes to the part where the diagnostic is reported (the attribute of any part applies to the whole type). It works with *Fix all in document / project / solution*.

```csharp
// before
public class OrderDto { public int Id { get; set; } }

// after
using System.Diagnostics.CodeAnalysis;

[ExcludeFromCodeCoverage]
public class OrderDto { public int Id { get; set; } }
```

The fix is offered only when `ExcludeFromCodeCoverageAttribute` exists in the project (it does in .NET Framework 4.0+, .NET Core and .NET 5+, .NET Standard 2.0+). `Justification` is available in recent versions of .NET: `code_fix_justification` adds it to the attribute.

## 📝 Included tools for code review

The `[DSA045] Add comment for code review` action inserts a structured block comment above the type. The comment includes the rule ID, enriched category, title with documentation link, and relevant external references.

## ⚙️ Rule configuration

### Severity

In order to change the severity level of this rule, change/add this line in the `.editorconfig` file:

```ini
# DSA045: A pure data carrier should be excluded from the code coverage
# Possible values: error, warning, suggestion, silent, none
dotnet_diagnostic.DSA045.severity = warning
```

### Which types are looked at

```ini
# The kinds of type that are looked at, comma separated: class, struct, record, record_struct (default: all four).
# To opt a kind out, list the others: for example "class, record" leaves structs and record structs alone.
dotnet_diagnostic.DSA045.included_type_kinds = class, struct, record, record_struct

# Abstract classes (default true)
dotnet_diagnostic.DSA045.include_abstract_classes = true

# Types declared inside another type (default true)
dotnet_diagnostic.DSA045.include_nested_types = true

# The minimum number of properties and fields (base types included) for a type to be a data carrier. 0: an empty type is one too (default 1)
dotnet_diagnostic.DSA045.min_data_members = 1
```

### What is "no logic"

```ini
# Instance fields are data, as properties are (default true)
dotnet_diagnostic.DSA045.allow_fields = true

# Initializers made of literals, constants and object creations are not logic (default true)
dotnet_diagnostic.DSA045.allow_property_initializers = true

# Old-style properties that an auto-property could replace (get { return _a; } set { _a = value; }) are data, and their private field is not counted (default true)
dotnet_diagnostic.DSA045.allow_backing_field_properties = true

# Expression-bodied properties and properties with accessor bodies are not logic (default false)
dotnet_diagnostic.DSA045.allow_computed_properties = false

# An explicit, empty, parameterless constructor is not logic (default false)
dotnet_diagnostic.DSA045.allow_parameterless_constructor = false

# Nested types do not make the type something else than a data carrier (default false)
dotnet_diagnostic.DSA045.allow_nested_types = false

# The base types must be data carriers too (default true). false: only the type itself is looked at.
dotnet_diagnostic.DSA045.inspect_base_types = true

# The opposite scenario (default true): report a type that has logic and is decorated with [ExcludeFromCodeCoverage].
dotnet_diagnostic.DSA045.report_excluded_types_with_logic = true
```

### What is already excluded, generated or out of scope

```ini
# Attributes (fully qualified names) that already exclude a type from the coverage. Replaces the default.
dotnet_diagnostic.DSA045.exclusion_attributes = System.Diagnostics.CodeAnalysis.ExcludeFromCodeCoverageAttribute

# Attributes (fully qualified names) of types that are not looked at. Replaces the default.
dotnet_diagnostic.DSA045.ignored_attributes = System.CodeDom.Compiler.GeneratedCodeAttribute, System.Runtime.CompilerServices.CompilerGeneratedAttribute

# Do not report in a test project, i.e. one that references one of the assemblies below (default true)
dotnet_diagnostic.DSA045.skip_test_assemblies = true
dotnet_diagnostic.DSA045.test_assembly_names = xunit.core, xunit.v3.core, nunit.framework, Microsoft.VisualStudio.TestPlatform.TestFramework, MSTest.TestFramework, TUnit.Core
```

### Exclusions

All the patterns are comma separated and case-insensitive; `*` matches any sequence of characters. All are empty by default, except the file patterns.

```ini
dotnet_diagnostic.DSA045.excluded_type_name_patterns = *Event, *Message
dotnet_diagnostic.DSA045.excluded_namespace_patterns = *.Generated
# Types that derive (directly or not) from one of these (fully qualified names)
dotnet_diagnostic.DSA045.excluded_base_types = My.Legacy.Entity
# File names. Replaces the default list: *.Designer.cs, *.generated.cs, *.g.cs, *.g.i.cs
dotnet_diagnostic.DSA045.excluded_file_patterns = *.Designer.cs, *.generated.cs, *.g.cs, *.g.i.cs
```

### Code fix

```ini
# The text of the Justification the code fix adds to the attribute (default: none).
# Needs a version of .NET where ExcludeFromCodeCoverageAttribute has the Justification property.
dotnet_diagnostic.DSA045.code_fix_justification = Data carrier, no logic
```
