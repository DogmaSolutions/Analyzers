# DSA037

A `[ThreadStatic]` field of type `System.Random` must not carry a field initializer. A thread-static field initializer runs only for the thread that first triggers the declaring type's static construction; every other thread observes the default value (`null`) and throws a `NullReferenceException` at first use.

## 💡 Rationale

A field marked `[ThreadStatic]` gets an independent storage slot per thread. A **field initializer**, however, is emitted into the type's static constructor, which the runtime runs **exactly once** — on the single thread that first triggers static construction. As a result the initializer assigns the value only for **that one thread**; on every other thread the field keeps its default value.

For a reference type such as `System.Random` the default is `null`, so the first access from any other thread throws a `NullReferenceException`:

```csharp
public static class Ids
{
    // BUG: only the first thread to touch Ids gets a Random; all others see null.
    [ThreadStatic]
    private static Random _rnd = new Random();

    public static int Next() => _rnd.Next(); // NRE on every thread except the initializing one
}
```

This is an especially common footgun because developers reach for `[ThreadStatic]` precisely to get a **per-thread** `Random` (since `System.Random` is not thread-safe) — the bug hides inside code that was trying to be correct about threading. The analyzer resolves `[ThreadStatic]` by symbol, so `[ThreadStatic]`, `[ThreadStaticAttribute]` and `[System.ThreadStatic]` all match while a user-defined same-named attribute does not; only an **initialized** `System.Random` declarator is flagged.

## 🔐 Security implications

- **CWE-457: Use of Uninitialized Variable** — on every thread other than the initializing one, the `[ThreadStatic]` field is observed in its default (`null`) state, i.e. used while effectively uninitialized. Beyond the immediate `NullReferenceException`, a subsequent attempt to work around the crash by sharing a single non-thread-safe `Random` across threads can corrupt its internal state and degrade the quality/uniqueness of the values produced.

## 🔦 Code sample

```csharp
public static class PerThreadRandom
{
    // this WILL trigger the rule: a [ThreadStatic] Random with a field initializer
    [ThreadStatic]
    private static Random _rndNotOk = new Random();

    // this WILL NOT trigger the rule: left uninitialized, assigned lazily per thread
    [ThreadStatic]
    private static Random? _rndOk;

    private static Random Rnd => _rndOk ??= new Random();

    public static int NextOk() => Rnd.Next();
}
```

## ℹ️  Matched patterns (code is NOT OK)

```cs
// Canonical case:
[ThreadStatic] private static Random _rnd = new Random();

// Any initializer expression, e.g. a factory call:
[ThreadStatic] private static Random _rnd = CreateRng();

// Target-typed new:
[ThreadStatic] private static Random _rnd = new();

// Multiple declarators — only the initialized one is flagged:
[ThreadStatic] private static Random _a = new Random(), _b; // _a is flagged
```

## ✅ Not matched patterns (code is OK)

```cs
// [ThreadStatic] field left uninitialized (assign lazily per thread):
[ThreadStatic] private static Random _rnd;

// A Random field initializer that is NOT [ThreadStatic]:
private static Random _rnd = new Random();

// A [ThreadStatic] field of some other type:
[ThreadStatic] private static int _counter = 0;

// A local variable (not a field):
Random rnd = new Random();
```

## 👉️ Rules of thumb for prevention and proactive posture

- Leave the `[ThreadStatic]` field **uninitialized** and assign a per-thread instance lazily on first use:

  ```csharp
  [ThreadStatic]
  private static Random? _rnd;

  private static Random Rnd => _rnd ??= new Random();
  ```

- On .NET 6+, prefer dropping `[ThreadStatic]` entirely in favour of the built-in thread-safe shared instance:

  ```csharp
  public static int Next() => Random.Shared.Next();
  ```
