# DSA046

A read-modify-write of a `volatile` field (`x++`, `x += v`, `x = f(x)`) is not atomic.

| Property     | Value                                                                                          |
|:-------------|:-----------------------------------------------------------------------------------------------|
| Rule ID      | DSA046                                                                                        |
| Title        | A read-modify-write of a volatile field is not atomic                                         |
| Category     | Code Smell                                                                                    |
| Severity     | ⚠ Warning                                                                                     |
| Refactoring available | ✅                                                                                             |
| Code-review tools available | ✅                                                                                             |
| Is enabled   | ✅                                                                                             |

## 💡 Rationale

`volatile` is often added to a field as a "make it thread safe" talisman. What it really does is narrow: a read of a volatile field has *acquire* semantics and a write has *release* semantics, so a thread that reads the field sees the latest value written by another thread, and the compiler and the CPU do not move other memory operations across the access in the forbidden direction.

It does **not** make a *sequence* of a read and a write indivisible. `x++` is shorthand for "read `x`, add one, write the result back", and another thread can run between the read and the write:

```csharp
public class HitCounter
{
    private volatile int _hits;

    public void Hit() => _hits++;      // DSA046
}
```

| Time | Thread A | Thread B | `_hits` |
|:-----|:---------|:---------|:--------|
| 1 | reads `5` | | `5` |
| 2 | | reads `5` | `5` |
| 3 | writes `6` | | `6` |
| 4 | | writes `6` | `6` |

Two calls, one increment: an update is lost. `volatile` made every single access visible, and the program is still wrong. The same happens with every compound assignment, and with an assignment whose value is computed from the field itself (`_on = !_on`, `_max = Math.Max(_max, v)`, `_handler = _handler ?? Create()`).

Races live **between** operations, not inside one. This is the same lesson as [DSA010](DSA010.md), told for `volatile` instead of `lock`.

## ✅ What is reported

| Operation | Examples | What is lost |
|:----------|:---------|:-------------|
| **Increment / decrement** | `x++`, `++x`, `x--`, `--x` | One of two concurrent updates |
| **Compound assignment** | `x += v`, `-=`, `*=`, `/=`, `%=`, `&=`, `\|=`, `^=`, `<<=`, `>>=`, `>>>=` (also delegates and strings: `h += handler`) | The update of the other thread |
| **Assignment from itself** | `x = x + 1`, `x = !x`, `x = Math.Max(x, v)`, `x = x ?? new T()`, `this.x = this.x + 1` | The update of the other thread; a toggle can be lost completely |

each one for three kinds of field, which change the advice in the message:

| Kind of field | Alternative the message suggests |
|:--------------|:---------------------------------|
| `int` | `Interlocked.Increment` / `Decrement` / `Add` / `Exchange`, or a `CompareExchange` loop for any other computation (every .NET version and platform); or a `lock` around **every** access |
| `uint` | the same methods, which exist for `uint` in .NET Core 2.0 and later and in .NET 5+, **not** in .NET Framework nor in .NET Standard 2.0 (the code fix is not offered there) |
| `float` | no `Increment` / `Add`, but `Interlocked.CompareExchange(ref float, ...)` exists on every .NET version: a compare-and-retry loop; or a `lock` |
| `nint` | no `Increment` / `Add`, but `Interlocked.CompareExchange(ref IntPtr, ...)` exists on every .NET version: a compare-and-retry loop; or a `lock` |
| `byte`, `sbyte`, `short`, `ushort`, `nuint` | no `Increment` / `Add`; `Exchange` / `CompareExchange` exist only in .NET 9 and later: widen to `int`, or take a `lock` |
| `bool`, `char` | no `Interlocked` overload in any .NET version: keep the value in an `int` field, or take a `lock` |
| An enum | no `Interlocked` overload in any .NET version: keep the value in an `int` field (and cast), or take a `lock` |
| Reference (delegate, string, object) | `Interlocked.CompareExchange` retried until the value you started from is still the current one, or a `lock`, or an immutable snapshot |

The field has to be `volatile`, of any accessibility, and accessed through its name, `this.` or another instance (`other.x++`). The diagnostic is located on the whole operation, and the message names the field and the operator.

## 🚫 What is *not* reported

| Case | Why |
|:-----|:----|
| Inside a `lock` statement (default, `skip_inside_lock`) | If every access of the field takes the same lock, the operation is atomic with respect to the others (and then `volatile` is not needed: see the alternatives). A lambda or a local function declared inside the lock is *not* exempted: it can run later |
| Inside a constructor (default, `skip_constructors`) | Nobody else can see the instance yet. A lambda or a local function of the constructor is not exempted |
| Plain assignment (`x = 0`, `x = other`, `x = v + 1`) | A write that does not depend on the current value cannot be lost in a harmful way: the last writer wins |
| `x = o.x + 1`, `o.x = x + 1` | The value comes from a different instance |
| Property, array element, member of a field (`_w.N++`), local variable | Not a `volatile` field |
| `x ??= v` | A lazy initialization, not a counter: see [DSA007](DSA007.md) |
| Generated files | `*.Designer.cs`, `*.g.cs`... are ignored |

## 🔧 Alternatives

| You want | Use |
|:---------|:----|
| A counter | `Interlocked.Increment(ref _hits)`; the field does not need `volatile` |
| A high-water mark (`max`) | A `CompareExchange` loop: read, compute, `CompareExchange`, retry if it failed |
| A flag that is switched once | `Interlocked.Exchange` / `CompareExchange`, or a `ManualResetEventSlim` / `CancellationToken` |
| A delegate that grows (`h += handler`) | A real `event` (the compiler generates the thread-safe `CompareExchange` loop), or a `lock` |
| Several fields that change together | A `lock` around the whole operation, or an immutable object swapped through a single field |

```csharp
public class HitCounter
{
    private int _hits;                                        // no volatile needed

    public void Hit() => Interlocked.Increment(ref _hits);    // atomic
    public int Hits => Volatile.Read(ref _hits);              // visible
}
```

Passing a `volatile` field by `ref` to `Interlocked` does not raise the compiler warning CS0420: the compiler knows the `Interlocked` methods.

## 🔧 Code fix

* **Use `Interlocked.Increment` / `Decrement` / `Add`**: offered for `x++`, `++x`, `x--`, `--x`, `x += v` and `x -= v` on an `int` or `uint` field, when the operation is a statement of its own. When the value of the expression is used the fix is not offered, because `Interlocked` returns the *new* value and `x++` the old one; `uint -=`, the other operators, assignments from the field itself and the other kinds of field need a decision of the developer. *Fix All* is supported.
* **Add comment for code review**: inserts a comment that references the rule, always offered.

## ⚙ Options

All options are set in the `.editorconfig`, under `dotnet_diagnostic.DSA046.<key>`.

| Key | Default | Meaning |
|:----|:--------|:--------|
| `severity` | `warning` | The severity of the rule |
| `report_increments` | `true` | Report `++` and `--` |
| `report_compound_assignments` | `true` | Report `+=`, `-=`, `\|=`... |
| `report_self_assignments` | `true` | Report `x = f(x)` |
| `report_interlocked_types` | `true` | Report the `int` and `uint` fields |
| `report_other_value_types` | `true` | Report the other value types (`bool`, `byte`, `short`, `char`, `float`, enums...) |
| `report_reference_types` | `true` | Report the fields that hold a reference (delegates, strings...) |
| `skip_inside_lock` | `true` | Do not report the operations inside a `lock` statement |
| `skip_constructors` | `true` | Do not report the operations in a constructor |
| `excluded_type_name_patterns` | *(empty)* | Glob patterns of the type names to ignore |
| `excluded_namespace_patterns` | *(empty)* | Glob patterns of the namespaces to ignore |
| `excluded_base_types` | *(empty)* | Types whose descendants are ignored |
| `excluded_field_name_patterns` | *(empty)* | Glob patterns of the field names to ignore |
| `excluded_file_patterns` | `*.Designer.cs, *.generated.cs, *.g.cs, *.g.i.cs` | Glob patterns of the files to ignore |


## 🔐 Security implications

A lost update in a counter that guards a quota, a retry limit, a sequence number or a "stop" flag is a sporadic, hard to reproduce defect, and can turn a limit into a suggestion.

* **CWE-362** — [Concurrent Execution using Shared Resource with Improper Synchronization ("Race Condition")](https://cwe.mitre.org/data/definitions/362.html)
* **CWE-366** — [Race Condition within a Thread](https://cwe.mitre.org/data/definitions/366.html)
* **CWE-820** — [Missing Synchronization](https://cwe.mitre.org/data/definitions/820.html)
