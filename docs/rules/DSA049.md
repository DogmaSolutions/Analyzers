# DSA049

A field guarded by a lock must be accessed under that lock everywhere.

| Property     | Value                                                                                          |
|:-------------|:-----------------------------------------------------------------------------------------------|
| Rule ID      | DSA049                                                                                        |
| Title        | A field guarded by a lock must be accessed under that lock everywhere                         |
| Category     | Code Smell                                                                                    |
| Severity     | ⚠ Warning                                                                                     |
| Refactoring available | ❌                                                                                             |
| Code-review tools available | ✅                                                                                             |
| Is enabled   | ✅                                                                                             |

## 💡 Rationale

A lock does not protect a variable. It excludes **the code that takes the same lock**, and nothing else. When a class writes a field under a lock in one member and touches the same field without that lock in another, the lock gives the false impression that the field is safe:

```csharp
public class TicketCounter
{
    private readonly object _gate = new object();
    private int _issued;

    public int Issue()
    {
        lock (_gate)
        {
            return ++_issued;
        }
    }

    public void Reset()
    {
        _issued = 0;                 // DSA049: not under _gate
    }

    public int Issued => _issued;    // DSA049: not under _gate
}
```

| Time | Thread A (`Issue`) | Thread B (`Reset`) | `_issued` |
|:-----|:-------------------|:-------------------|:----------|
| 1 | takes `_gate`, reads `41` | | `41` |
| 2 | | writes `0` (no lock to wait for) | `0` |
| 3 | writes `42` | | `42` |

The reset was lost, and the lock was there the whole time. A read has the same problem in a milder form: without the lock it can run in the middle of a locked sequence, and, without `volatile`, nothing guarantees it sees the latest value.

## ✅ What is reported

For a field that is **written under a lock** somewhere in the type, and that is not `readonly`, `const`, `[ThreadStatic]`, or handed by `ref`/`out` anywhere (`Interlocked.Increment(ref _x)` means the field follows a lock-free protocol), every access of the field that does not hold that lock:

| Scenario | The access | The lesson |
|:---------|:-----------|:-----------|
| **Unlocked write** | An assignment, `++`/`--`, compound assignment or tuple assignment that holds no lock | The write can run at the same time as the locked ones, and lose or corrupt their updates. Take the same lock |
| **Unlocked read** | A read that holds no lock, of a field that is not `volatile` | The read can see a stale or half-updated value. Take the same lock; for a single value make the field `volatile`; or publish an immutable snapshot under the lock |
| **Write under a different lock** | A write that holds another lock | Two different locks do not exclude each other. Use one lock for the field |

The lock that guards the field is the one held by most of its locked writes. The diagnostic is located on the field access, and the message names the field, the guarding lock, a member that writes the field under it, and, for a different lock, the lock that is held.

### Which locks are held at an access

* The `lock` statements around it, in the same member (a lambda or a local function written inside a `lock` counts as inside it).
* The locks that **all the callers** of its private method hold: a private helper that is only ever called from locked code is locked code (`infer_locks_of_private_helpers`, followed through helpers of helpers). A private method that is also used as a method group, or called from an unlocked place, inherits nothing.

## 🚫 What is *not* reported

| Case | Why |
|:-----|:----|
| Accesses in a constructor, a static constructor, a finalizer, a field initializer or a `Dispose` method | Nobody else can see the object yet, or any more |
| A `volatile` field that is read | A volatile read sees the latest write. Writes of a volatile field are still reported: the lock does not exclude them |
| A field that is read under *another* lock | It is not this rule's business; the writes tell whether the locks agree |
| A field that is only written without locks, or only accessed under the lock | There is no lock protocol to be inconsistent with |
| `readonly` fields, constants, `[ThreadStatic]` fields, fields handed by `ref`/`out` (`Interlocked`, `Volatile`) | Immutable, per-thread, or lock-free by design |
| The **content** of a collection (`_items.Add(x)`, `_items.Count`) | The rule looks at the field itself (its value), not at what the object it points to does |
| Generated files | `*.Designer.cs`, `*.g.cs`... are ignored |

All the parts of a `partial` type are inspected, and a nested type is analyzed on its own.

## 🔧 Alternatives

| You want | Use |
|:---------|:----|
| One field with several writers and readers | The same lock in **every** access, or a property that wraps the field and takes the lock, and nothing else touches the field |
| A flag or a single value | `volatile` for the readers **and** a lock or `Interlocked` for the writers that read-modify-write ([DSA046](DSA046.md)) |
| A counter | `Interlocked.Increment` / `Interlocked.Add`, with no lock at all |
| Several fields that change together | One lock around **every** access of all of them, or an immutable object swapped through a single field |
| Reads that must not block | Copy-on-write: build a new immutable object under the lock, publish it with a `volatile` write, read it without a lock |

```csharp
public class TicketCounter
{
    private int _issued;                            // touched only through Interlocked

    public int Issue() => Interlocked.Increment(ref _issued);
    public void Reset() => Interlocked.Exchange(ref _issued, 0);
    public int Issued => Volatile.Read(ref _issued);
}
```

## 🔧 Code fix

* **Add comment for code review**: inserts a comment that references the rule. The right remedy (take the same lock, `volatile`, `Interlocked`, an immutable snapshot) depends on what the code does with the value, so no automatic rewrite is offered.

## ⚙ Options

All options are set in the `.editorconfig`, under `dotnet_diagnostic.DSA049.<key>`.

| Key | Default | Meaning |
|:----|:--------|:--------|
| `severity` | `warning` | The severity of the rule |
| `report_unlocked_writes` | `true` | Report the writes that hold no lock |
| `report_unlocked_reads` | `true` | Report the reads that hold no lock |
| `report_different_locks` | `true` | Report the writes that hold another lock |
| `infer_locks_of_private_helpers` | `true` | A private method holds the locks all its callers hold |
| `excluded_type_name_patterns` | *(empty)* | Glob patterns of the type names to ignore |
| `excluded_namespace_patterns` | *(empty)* | Glob patterns of the namespaces to ignore |
| `excluded_base_types` | *(empty)* | Types whose descendants are ignored |
| `excluded_field_name_patterns` | *(empty)* | Glob patterns of the field names to ignore |
| `excluded_member_name_patterns` | *(empty)* | Glob patterns of the names of the members whose accesses are ignored |
| `excluded_file_patterns` | `*.Designer.cs, *.generated.cs, *.g.cs, *.g.i.cs` | Glob patterns of the files to ignore |

```ini
[*.cs]
dotnet_diagnostic.DSA049.severity = warning
dotnet_diagnostic.DSA049.report_unlocked_reads = false
dotnet_diagnostic.DSA049.excluded_member_name_patterns = Reset*
```

## 🔐 Security implications

A shared quota, a session state, an authorization flag or a retry counter that is protected by a lock in some code paths and not in others can be corrupted by exactly the path nobody tested.

* **CWE-366** — [Race Condition within a Thread](https://cwe.mitre.org/data/definitions/366.html)
* **CWE-567** — [Unsynchronized Access to Shared Data in a Multithreaded Context](https://cwe.mitre.org/data/definitions/567.html)
* **CWE-820** — [Missing Synchronization](https://cwe.mitre.org/data/definitions/820.html)
