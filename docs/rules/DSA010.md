# DSA010

A lock around a single field access does not protect your logic.

| Property     | Value                                                                                          |
|:-------------|:-----------------------------------------------------------------------------------------------|
| Rule ID      | DSA010                                                                                        |
| Title        | A lock around a single field access does not protect your logic                               |
| Category     | Code Smell                                                                                    |
| Severity     | ⚠ Warning                                                                                     |
| Refactoring available | ❌                                                                                             |
| Code-review tools available | ✅                                                                                             |
| Is enabled   | ✅                                                                                             |

## 💡 Rationale

A very common belief, especially among developers who are new to multithreading, is that thread safety is something you can *attach to a variable*: wrap every read and every write of the field in a `lock`, and "the field is protected".

```csharp
private readonly object _gate = new object();
private bool _isRunning;

private bool IsRunning
{
    get { lock (_gate) { return _isRunning; } }   // DSA010
    set { lock (_gate) { _isRunning = value; } }  // DSA010
}
```

**It is not.** A race condition is never *inside* a single read or a single write: reading a `bool`, an `int` or a reference, and assigning it, are already indivisible operations. Races live **between** operations: the caller reads the property, takes a decision, and then writes. The lock is released after the read and taken again for the write, and in the gap any other thread can run.

```csharp
public void Start()
{
    if (!IsRunning)        // 1. read  (locked, then unlocked)
    {                      //    <-- another thread can run here
        IsRunning = true;  // 2. write (locked, then unlocked)
        new Thread(Run).Start();
    }
}
```

| Time | Thread A | Thread B | `_isRunning` |
|:-----|:---------|:---------|:-------------|
| 1 | `IsRunning` → `false` | | `false` |
| 2 | | `IsRunning` → `false` | `false` |
| 3 | `IsRunning = true` | | `true` |
| 4 | starts the worker | `IsRunning = true` | `true` |
| 5 | | starts the **second** worker | `true` |

Every individual access was "protected", and the program is still wrong. The locks only gave the developer the *feeling* of safety, which is worse than having none: nobody will look for the bug there.

What a lock really protects is an **invariant**: a rule that involves *more than one* operation, such as "check, then act", "read, modify, write", or "these three fields change together". To protect it, **one** critical section must surround the **whole** sequence.

The rule fires on every `lock` statement whose body is nothing but one plain read (`return field;`) or one plain assignment (`field = value;`) of a field of the same type.

### What a single-access lock still does (and why it should be said explicitly)

The rule is not a claim that the lock compiles to nothing. A single-access lock has a few real, side effects. They are almost never what the author had in mind, and they are all available in a more honest, cheaper and self-documenting form:

| Side effect of the lock | When it matters | What to write instead |
|:------------------------|:----------------|:----------------------|
| **Visibility and ordering** (a lock is an acquire/release barrier): another thread sees the new value, and everything written before it | A flag or a value that is read by a different thread, possibly in a loop | `volatile`, or `Volatile.Read` / `Volatile.Write`, or better a `CancellationToken` for "stop" flags |
| **Prevents tearing** of values that are wider than the CPU native word | `long`, `ulong`, `double` in a 32-bit process; `decimal`, `Guid`, `DateTime`, `TimeSpan`, `Nullable<T>`, tuples and any struct, everywhere | `Interlocked.Read` / `Interlocked.Exchange` for 64-bit values, or an **immutable object swapped by reference** |
| **Makes the caller wait** while another thread is inside a longer critical section on the same lock | The lock is shared with a longer operation | Say so: take the lock around the whole operation, or use the proper signaling primitive |
| Full memory fence (store-load ordering) | Lock-free algorithms of the Dekker/Peterson family | `Interlocked` operations or `Thread.MemoryBarrier` |

The messages of the rule mention the relevant side effect for each scenario, so that a developer who actually *needs* one of them knows how to say it clearly.

### What `volatile` does, and what it does not

`volatile` is the other tool developers reach for to "make a field thread safe". It is narrower than it looks: a read has *acquire* semantics and a write has *release* semantics, so a thread that reads the field sees the latest value written by another thread, and the compiler and the CPU do not move other memory operations across the access in the forbidden direction. That is all.

| Belief | Reality |
|:-------|:--------|
| "`volatile` makes `_counter++` atomic" | `++`, `+=` and `_x = _x + 1` are a read followed by a write: two threads can both read `5` and both write `6`. Use `Interlocked` or a `lock` |
| "The object the field points to is protected" | `volatile` applies to the **reference** (or the value) held by the field, never to the state of the object it points to. A mutable object needs its own synchronization |
| "`volatile` makes check-then-act safe" | Races live *between* operations (`if (!_started) { _started = true; ... }`), exactly as with the locks above |
| "`volatile` is harmless, so add it just in case" | It costs a memory barrier on every access, and tells the next reader that the class has a concurrency story. A `volatile` field that is only given its value by its initializer or its constructors never changes, and has nothing to make visible: declare it `readonly` (the IDE0044 *Make field readonly* style rule of the .NET SDK reports it, `volatile` fields included) |

## 🔐 Security implications

Race conditions in the state of a component (a "stop" flag, an authorization or session state, a counter that guards a quota) are a source of sporadic, hard to reproduce and sometimes exploitable defects:

* **CWE-667** — [Improper Locking](https://cwe.mitre.org/data/definitions/667.html)
* **CWE-362** — [Concurrent Execution using Shared Resource with Improper Synchronization ("Race Condition")](https://cwe.mitre.org/data/definitions/362.html)
* **CWE-820** — [Missing Synchronization](https://cwe.mitre.org/data/definitions/820.html)

## 🔦 Code sample

```csharp
public class JobRunner
{
    private readonly object _gate = new object();
    private bool _isRunning;
    private int _done;

    public bool IsRunning
    {
        // this WILL trigger the rule: a lock around a single read
        get { lock (_gate) { return _isRunning; } }

        // this WILL trigger the rule: a lock around a single assignment
        set { lock (_gate) { _isRunning = value; } }
    }

    // this WILL NOT trigger the rule: ONE critical section around the whole check-then-act
    public bool TryStart()
    {
        lock (_gate)
        {
            if (_isRunning)
                return false;

            _isRunning = true;
            return true;
        }
    }

    // this WILL NOT trigger the rule: the critical section does more than one thing
    public void Add(int count)
    {
        lock (_gate)
        {
            _done += count;
        }
    }
}
```

## ℹ️  Matched patterns (code is NOT OK)

```cs
// A property whose accessors lock the same object around a single access (the classic):
private bool IsRunning { get { lock (_gate) { return _isRunning; } } set { lock (_gate) { _isRunning = value; } } }

// The same, in methods:
public bool GetIsRunning() { lock (_gate) { return _isRunning; } }
public void SetIsRunning(bool value) { lock (_gate) { _isRunning = value; } }

// Embedded statement, this.-qualified field, parenthesized expression, constant or parameter assigned:
get { lock (_gate) return this._isRunning; }
set { lock (_gate) { _isRunning = false; } }
public void Reset(int v) { lock (_gate) { _count = -v; } }

// Also when the lock is shared with other, longer critical sections of the class:
public void Work() { lock (_gate) { _a++; _b++; } }          // the long one
public bool Flag { get { lock (_gate) { return _flag; } } }  // DSA010

// lock (this) (opt-in, see report_lock_on_this):
get { lock (this) { return _flag; } }
```

## ✅ Not matched patterns (code is OK)

```cs
// The critical section is a sequence of operations (check-then-act, read-modify-write, several fields):
lock (_gate) { if (!_isRunning) { _isRunning = true; start = true; } }
lock (_gate) { _count += value; }
lock (_gate) { _a = value; _b = value; }

// The critical section calls something (a collection is not thread-safe, the lock is what protects it):
lock (_gate) { _items.Add(item); }

// What is assigned reads other shared state: the lock may be keeping two fields consistent
lock (_gate) { _copy = _original; }

// The lock object is not private, or it can be reached from outside the class:
public readonly object Gate = new object();
lock (Gate) { return _flag; }
public object GetGate() => _gate;     // the lock escapes: other code may rely on it

// The lock is part of a signaling protocol (Monitor.Pulse / PulseAll on the same lock):
lock (_gate) { Monitor.PulseAll(_gate); }

// The lock object is replaced after construction: its identity is not stable
public void Reset() { _gate = new object(); }
```

## 👉️ Rules of thumb for prevention and proactive posture

1. **Ask which invariant you are protecting.** If you cannot name a rule that involves two or more operations or fields, the lock protects nothing.
2. **Protect operations, not variables.** The unit of locking is the whole check-then-act or read-modify-write sequence, in **one** critical section.
3. **Do not expose a property that hides a lock.** A property named `IsRunning` that locks invites callers to write `if (!IsRunning) IsRunning = true;`. Expose the *operation* instead (`TryStart()`, `TryStop()`), where the lock is held for the whole decision.
4. **Prefer the dedicated primitive** when one fits (table below).
5. **Prefer immutable snapshots** for values that change together: replace the whole object by reference instead of changing its fields one by one.
6. **Never `lock (this)`**, `lock (typeof(X))` or on a string/public object: any other code can take the same lock and block you or deadlock you.
7. **Do not hold a lock while calling unknown code** (events, callbacks, hardware or network I/O): the lock is held for as long as the callee takes, and the callee may try to take another lock.
8. Document the thread-safety contract of the class: which members can be called from which threads.

### Which tool for which need

| You need… | Use | Instead of |
|:----------|:----|:-----------|
| A "please stop" signal for a worker | `CancellationTokenSource` / `CancellationToken` | a `bool` property read in a loop |
| Run an action only once, or start only if idle | `Interlocked.CompareExchange(ref _state, Running, Idle) == Idle` or one `lock` around check and act | `if (!IsRunning) IsRunning = true;` |
| A counter | `Interlocked.Increment` / `Add` | `lock { _n++; }` per access, or a locked property |
| Other threads to see the latest value of a flag | `volatile` / `Volatile.Read` / `Volatile.Write` | a lock around the single access |
| Several values that change together | one `lock` around the whole update **and** the whole read, or an immutable object replaced by reference | one lock per field |
| A 64-bit value (`long`, `double`) shared between threads, also in 32-bit processes | `Interlocked.Read` / `Exchange`, or an immutable snapshot | a lock around each access, undocumented |
| A thread-safe collection | `ConcurrentDictionary`, `ConcurrentQueue`, `ConcurrentBag`, `System.Threading.Channels` | a `List<T>`/`Dictionary` with locks on the property |
| Mutual exclusion that spans an `await` | `SemaphoreSlim(1, 1)` (`lock` cannot contain `await`) | `lock` + blocking waits |
| Lazy, thread-safe initialization | `Lazy<T>` with `LazyThreadSafetyMode.ExecutionAndPublication` | hand-made double-checked locking ([DSA007](DSA007.md)) |

## 🛠️ Included Code Fixer and Mitigation

The right remedy (lock the whole operation, `volatile`, `Interlocked`, a cancellation token, an immutable snapshot) depends on what the rest of the class does with the value. Removing the lock mechanically would hide the problem and could silently drop a visibility or tearing guarantee someone relies on, so the rule offers no automatic fix. It offers the *Add comment for code review* action only.

## 📝 Included tools for code review

The `[DSA010] Add comment for code review` action inserts a structured block comment above the `lock` statement. The comment includes the rule ID, enriched category, title with documentation link, and relevant external references.

## 🔁 Before and after

### A start/stop flag

```csharp
// BEFORE: every access is locked, the logic is racy (start twice, "stopped" raised twice)
public class JobRunner
{
    private readonly object _gate = new object();
    private bool _isRunning;
    private bool IsRunning { get { lock (_gate) { return _isRunning; } } set { lock (_gate) { _isRunning = value; } } }

    public void Start()
    {
        if (!IsRunning)
        {
            IsRunning = true;
            new Thread(Run).Start();
        }
    }

    public void Stop()
    {
        if (IsRunning)
        {
            IsRunning = false;
            Stopped?.Invoke(this, EventArgs.Empty);
        }
    }
}
```

```csharp
// AFTER (option 1): one atomic state transition, no lock at all
public class JobRunner
{
    private int _state; // 0 = idle, 1 = running

    public bool IsRunning => Volatile.Read(ref _state) == 1;

    public void Start()
    {
        if (Interlocked.CompareExchange(ref _state, 1, 0) == 0)
            new Thread(Run).Start();
    }

    public void Stop()
    {
        if (Interlocked.Exchange(ref _state, 0) == 1)
            Stopped?.Invoke(this, EventArgs.Empty);
    }
}
```

```csharp
// AFTER (option 2): ONE critical section around each decision
public class JobRunner
{
    private readonly object _gate = new object();
    private bool _isRunning;

    public void Start()
    {
        lock (_gate)
        {
            if (_isRunning)
                return;

            _isRunning = true;
        }

        new Thread(Run).Start();
    }

    public void Stop()
    {
        lock (_gate)
        {
            if (!_isRunning)
                return;

            _isRunning = false;
        }

        Stopped?.Invoke(this, EventArgs.Empty); // outside the lock: unknown code is never called while holding it
    }
}
```

### Values that change together

```csharp
// BEFORE: three locked properties, a reader can combine the latency of one run with the throughput of another
private double Latency { get { lock (_gate) { return _latency; } } set { lock (_gate) { _latency = value; } } }
private double Throughput { get { lock (_gate) { return _throughput; } } set { lock (_gate) { _throughput = value; } } }

// AFTER: one immutable snapshot, replaced by reference (a reference write is atomic, and the reader gets a consistent pair)
public sealed record Sample(double Latency, double Throughput);

private Sample _sample = new Sample(0, 0);

public Sample Current => Volatile.Read(ref _sample);

private void Publish(double latency, double throughput) => Volatile.Write(ref _sample, new Sample(latency, throughput));
```

## 🧭 The scenarios and their messages

Every scenario has a message of its own, a small lesson on what is wrong with that specific lock.

| Scenario | Access | Lock | Field | The message teaches |
|:---------|:-------|:-----|:------|:--------------------|
| 1 | read | dedicated | plain | a single read is atomic and nobody else takes the lock; races are between operations; lock the whole operation or use `volatile` |
| 2 | write | dedicated | plain | a single assignment is atomic; the race is in check-then-act and read-modify-write; use `volatile` / `Interlocked` for visibility or atomic updates |
| 3 | read | dedicated | tearable | no logic protected; at most it prevents torn reads, so say so (`Interlocked.Read`, immutable snapshot) |
| 4 | write | dedicated | tearable | same, for torn writes (`Interlocked.Exchange`, immutable snapshot) |
| 5 | read | shared | plain | the lock only orders memory and makes the reader wait behind the other critical sections; say it explicitly or remove it |
| 6 | write | shared | plain | the same for the writer; a multi-step invariant needs one critical section around the whole sequence |
| 7 | read | shared | tearable | ordering, waiting, and possibly preventing torn reads: express the one you need |
| 8 | write | shared | tearable | the same, for writes |
| 9 | read | `this` | plain | one atomic read needs no lock; locking `this` exposes the lock to every caller (deadlocks); use a private lock around the whole operation |
| 10 | write | `this` | plain | the same for writes |
| 11 | read | `this` | tearable | as 9, plus the torn-read explanation |
| 12 | write | `this` | tearable | as 10, plus the torn-write explanation |
| 13 | read | any | `volatile` | a volatile read already sees the latest value; the lock adds nothing |
| 14 | write | any | `volatile` | a volatile write is already published; the lock adds nothing |
| 15 | read | any | `readonly` | the field never changes after construction; the lock protects nothing and only makes readers wait; protect the operations on the pointed object instead |

*Dedicated* means that the lock is only ever taken around single accesses like this one. *Shared* means that some other critical section of the class (or a `Monitor.Wait`, `Enter`...) takes the same lock too. *Tearable* means a value that is wider than the native word of the CPU, or made of several fields (`long`, `ulong`, `double`, `decimal`, `DateTime`, `TimeSpan`, `Guid`, `Nullable<T>`, tuples, structs, unconstrained generic type parameters, enums backed by a 64-bit type).

## ⚙️ Rule configuration

### Severity

In order to change the severity level of this rule, change/add this line in the `.editorconfig` file:

```ini
# DSA010: A lock around a single field access does not protect your logic
# Possible values: error, warning, suggestion, silent, none
dotnet_diagnostic.DSA010.severity = warning
```

### Which accesses and fields are reported

```ini
# Critical sections that read a field (default true)
dotnet_diagnostic.DSA010.report_reads = true

# Critical sections that assign a field (default true)
dotnet_diagnostic.DSA010.report_writes = true

# Locks that other, longer critical sections of the class take too (default true).
# false: only the locks that are used for nothing else are reported.
dotnet_diagnostic.DSA010.report_shared_locks = true

# lock (this) (default false: other code may take the same lock to coordinate with the instance)
dotnet_diagnostic.DSA010.report_lock_on_this = false

# Fields wider than the CPU native word (long, double, decimal, structs...), where a lock may be there to prevent torn reads (default true)
dotnet_diagnostic.DSA010.report_tearable_types = true

# volatile fields (default true)
dotnet_diagnostic.DSA010.report_volatile_fields = true

# readonly fields (default true)
dotnet_diagnostic.DSA010.report_readonly_fields = true

# true (default): do not report a lock that is signaled with Monitor.Pulse / PulseAll anywhere in the class
dotnet_diagnostic.DSA010.skip_signaled_locks = true
```

### Where the critical section is

```ini
# sole_statement (default): the lock statement must be the only statement of the member (the usual accessor or getter/setter method).
# any_statement: every lock statement of the member is looked at.
dotnet_diagnostic.DSA010.body_shape = sole_statement

# The kinds of member that are looked at, comma separated: accessor, method, local_function, lambda, constructor, other.
# Default: accessor, method. An empty or invalid value falls back to the default.
dotnet_diagnostic.DSA010.member_kinds = accessor, method
```

### Exclusions

All the patterns are comma separated and case-insensitive; `*` matches any sequence of characters. All are empty by default, except the file patterns.

```ini
# Types (by name) and namespaces to skip
dotnet_diagnostic.DSA010.excluded_type_name_patterns = *Dto, *Options
dotnet_diagnostic.DSA010.excluded_namespace_patterns = *.Generated

# Types that derive (directly or not) from one of these (fully qualified names)
dotnet_diagnostic.DSA010.excluded_base_types = My.Legacy.ThreadSafeBase

# Properties, indexers (named "this[]"), events, methods and local functions to skip
dotnet_diagnostic.DSA010.excluded_member_name_patterns = Get*, Set*

# Fields, lock objects, and types of fields (as written by the compiler: int, bool, System.DateTime...) to skip
dotnet_diagnostic.DSA010.excluded_field_name_patterns = _tick*
dotnet_diagnostic.DSA010.excluded_lock_name_patterns = _sync*
dotnet_diagnostic.DSA010.excluded_field_types = System.DateTime, System.Guid

# Files to skip (file names). Replaces the default list: *.Designer.cs, *.generated.cs, *.g.cs, *.g.i.cs
dotnet_diagnostic.DSA010.excluded_file_patterns = *.Designer.cs, *.generated.cs, *.g.cs, *.g.i.cs, *.Legacy.cs
```

Generated code is never analyzed, whatever the options.

### Suppressing a single occurrence

```csharp
#pragma warning disable DSA010 // the lock is there to prevent torn reads of a 64-bit value on 32-bit platforms
get { lock (_gate) { return _total; } }
#pragma warning restore DSA010
```

A short comment that says *why* is exactly what the rule asks for: it turns an undocumented belief into a documented decision.
