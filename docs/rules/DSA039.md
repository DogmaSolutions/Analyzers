# DSA039

Reducing the output of `System.Security.Cryptography.RandomNumberGenerator` into a range with the remainder operator (`%`) introduces modulo bias: unless the range divides the operand domain evenly, the lower residues occur more often, skewing a value that was meant to be uniform and defeating the point of using a cryptographic generator. Use `RandomNumberGenerator.GetInt32(fromInclusive, toExclusive)` instead.

## 💡 Rationale

`System.Security.Cryptography.RandomNumberGenerator` produces uniformly distributed bytes. Reducing them into a smaller range with the remainder operator (`%`) reintroduces bias unless the range size exactly divides the operand's value domain (e.g. `2^32` for an `int`). When it does not, the lower residues occur slightly more often than the higher ones, so the result is no longer uniform — silently weakening tokens, PINs, keys and other security-sensitive values, and defeating the whole reason for choosing a cryptographic generator.

```csharp
// BUG: modulo bias — the lower residues are very slightly more likely.
byte[] buffer = new byte[4];
RandomNumberGenerator.Fill(buffer);
int dieRoll = BitConverter.ToInt32(buffer, 0) % 6;
```

This rule flags a `%` whose left operand is an integer derived from `RandomNumberGenerator` output — a `BitConverter.ToIntXX(...)` conversion of, or an element access into, RNG-filled bytes, including a one-hop local buffer. It targets only the integral case, follows data flow **one hop** within the same method, and deliberately favours precision over recall.

## 🔐 Security implications

- **CWE-1241: Use of Predictable Algorithm in Random Number Generator** — a biased reduction makes the output distribution non-uniform and therefore partially predictable.
- **CWE-338: Use of Cryptographically Weak PRNG (family)** — the bias undermines the cryptographic guarantee the generator was chosen to provide, weakening any secret derived from it.

## 🔦 Code sample

```csharp
public class Tokens
{
    public int SmallRange_NotOk()
    {
        // this WILL trigger the rule: % over an integer derived from RNG bytes
        byte[] buffer = new byte[4];
        RandomNumberGenerator.Fill(buffer);
        return BitConverter.ToInt32(buffer, 0) % 6;
    }

    public int SmallRange_Ok()
    {
        // this WILL NOT trigger the rule: rejection-sampled, unbiased
        return RandomNumberGenerator.GetInt32(0, 6);
    }
}
```

## ℹ️  Matched patterns (code is NOT OK)

```cs
// BitConverter over a locally RNG-filled buffer:
byte[] b = new byte[4];
RandomNumberGenerator.Fill(b);
int x = BitConverter.ToInt32(b, 0) % n;

// BitConverter directly over GetBytes:
int y = BitConverter.ToInt32(RandomNumberGenerator.GetBytes(4), 0) % n;

// Indexing RNG bytes:
int z = RandomNumberGenerator.GetBytes(1)[0] % 6;

// One-hop local integer:
int raw = BitConverter.ToInt32(RandomNumberGenerator.GetBytes(4), 0);
int r = raw % n;
```

## ✅ Not matched patterns (code is OK)

```cs
// The correct, unbiased API:
int ok = RandomNumberGenerator.GetInt32(0, n);

// % on a value not derived from RNG:
int a = someInt % n;

// System.Random modulo is a different concern, not this rule:
int b = new Random().Next() % n;

// RNG bytes used without a % reduction:
byte[] key = RandomNumberGenerator.GetBytes(32);
```

## 👉️ Rules of thumb for prevention and proactive posture

- Use `RandomNumberGenerator.GetInt32(fromInclusive, toExclusive)`, which performs rejection sampling and returns an unbiased value in the requested range:

  ```csharp
  int dieRoll = RandomNumberGenerator.GetInt32(0, 6); // uniform in [0, 6)
  ```

- Never reduce raw cryptographic bytes with `%` unless the range is a power of two that divides the operand domain exactly.
- The rule is intentionally high-precision: only the integral `%` case is flagged, only one data-flow hop is followed, and cross-method flow is out of scope. A biased reduction split across methods will not be caught, so keep the unbiased API as the team default.
