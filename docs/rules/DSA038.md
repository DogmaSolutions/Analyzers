# DSA038

A `System.Random` constructed with a seed that is either a time-based value (e.g. `Environment.TickCount`, `DateTime.UtcNow.Ticks`) or a compile-time constant. A time-based seed is redundant with the parameterless constructor and, because it is derived from a low-resolution clock, several instances created within the same tick share a seed and therefore emit the identical sequence. A constant seed produces a fully deterministic, predictable sequence.

## 💡 Rationale

`new Random(seed)` is almost always a mistake in one of two ways.

**Time-based seed** — `new Random(Environment.TickCount)`, `new Random((int)DateTime.UtcNow.Ticks)`, `new Random((int)Stopwatch.GetTimestamp())`, etc. This merely reproduces what the parameterless `new Random()` already does internally, but worse: the clock has coarse resolution, so several `Random` instances created within the **same tick** — the classic "new `Random` inside a loop" bug — receive the **same seed** and emit the **identical sequence**.

```csharp
// BUG: every instance created in the same millisecond returns the same numbers.
for (int i = 0; i < 100; i++)
{
    var rnd = new Random(Environment.TickCount);
    Console.WriteLine(rnd.Next());
}
```

**Constant seed** — `new Random(42)`. The sequence is fully deterministic and predictable. That is occasionally desirable for a reproducible simulation or a unit test, but is a defect in production code (and never a source of security-grade randomness). The analyzer classifies a time-based value first (it is a property/method call, never a compile-time constant) and otherwise falls back to a compile-time-constant check; the recommended parameterless constructor is never flagged.

## 🔐 Security implications

- **CWE-337: Predictable Seed in Pseudo-Random Number Generator** — a constant seed makes the whole sequence predictable, and a time-based seed narrows it to the small set of clock values around the moment of construction. Where the produced values gate anything security-relevant, an attacker who can guess or observe the seed can reproduce the sequence. Security-sensitive values (tokens, keys, salts) must not use `System.Random` at all — use `System.Security.Cryptography.RandomNumberGenerator` (see DSA040).

## 🔦 Code sample

```csharp
public class Dice
{
    public int Roll_NotOk()
    {
        // this WILL trigger the rule: time-based seed collides within a clock tick
        var rnd = new Random(Environment.TickCount);
        return rnd.Next(1, 7);
    }

    public int Roll_Ok()
    {
        // this WILL NOT trigger the rule: parameterless constructor
        var rnd = new Random();
        return rnd.Next(1, 7);
    }
}
```

## ℹ️  Matched patterns (code is NOT OK)

```cs
new Random(Environment.TickCount);
new Random(Environment.TickCount64);
new Random((int)DateTime.Now.Ticks);
new Random((int)DateTime.UtcNow.Ticks);
new Random(unchecked((int)DateTimeOffset.UtcNow.Ticks));
new Random((int)System.Diagnostics.Stopwatch.GetTimestamp());
new Random(42);                 // compile-time constant
const int Seed = 7; new Random(Seed);
```

## ✅ Not matched patterns (code is OK)

```cs
new Random();                   // parameterless — the recommended form
new Random(GetSeedFromConfig()); // non-constant, non-time-based runtime value
new Random(userSuppliedSeed);   // a parameter is neither constant nor time-based
```

## 👉️ Rules of thumb for prevention and proactive posture

- Use the parameterless constructor, which is seeded for you with a high-entropy, per-instance value on modern .NET:

  ```csharp
  var rnd = new Random();       // correct
  int n = Random.Shared.Next(); // .NET 6+, thread-safe
  ```

- Reserve seeded construction for code that genuinely needs a reproducible sequence (e.g. a test project), and scope the severity down for that path only:

  ```ini
  [tests/**.cs]
  dotnet_diagnostic.DSA038.severity = none
  ```

- Never derive a seed from the current time by hand, and never use `System.Random` for security-sensitive values.
